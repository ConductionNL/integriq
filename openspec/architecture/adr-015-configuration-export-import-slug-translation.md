# ADR-015: Configuration export / import portability via slug translation

## Status
Accepted (capturing existing decision)

## Date
2026-05-20

## Context

Integriq configurations (Sources, Endpoints, Mappings, Rules, Jobs,
Synchronizations) are identified in the database by auto-increment integer
primary keys. When a configuration is exported from one environment (e.g.
development) and imported into another (e.g. production), the integer PKs in
the source environment do not match any PKs in the target environment.
Cross-entity references — `Endpoint.targetId`, `Synchronization.sourceId`,
`Synchronization.targetId`, `Endpoint.inputMapping`, `Endpoint.outputMapping`,
`Endpoint.rules[]` — would be meaningless in the target environment if stored
as integers.

ADR-008 references `ConfigurationService::exportEndpoint()` as a place that
must slug-translate `targetId` for portability. ADR-009 references
`ConfigurationService.php:275-295` and `:547-557` as sites that perform
register/schema ID→slug translation. But no ADR documents the full contract:
which fields get translated, in which direction, by what mechanism, and how the
slug-vs-uuid strategy will change after chain B introduces OR uuids as the new
FK format.

## Decision

**Slug as the cross-environment identity primitive**

Human-readable `slug` strings (e.g. `"my-api-source"`, `"customer-endpoint"`)
are the portability identity for Integriq entities. Slugs are unique per
resource type within an installation and are authored by the administrator
rather than generated by the database. This makes them stable across environment
promotions, version upgrades, and database restores.

UUIDs assigned by OpenRegister after chain B are an in-environment identity
(stable within one installation but different across environments if objects
were created independently). UUIDs MUST NOT be stored in exported configuration
for cross-environment FK references; slugs continue to be the portable FK
representation.

**Translation at export time (ID → slug)**

`ConfigurationService::exportConfiguration()` (and the
`exportEndpointsByConfiguration()` variant) always calls `resetMappings()`
first (`lib/Service/ConfigurationService.php:188-219`). `resetMappings()`
pre-populates two lookup tables for each of the eight translatable entity types
(`endpoint`, `synchronization`, `mapping`, `rule`, `source`, `register`,
`schema`, `job`):
- `$this->mappings['<type>']['idToSlug']` — integer-PK → slug
- `$this->mappings['<type>']['slugToId']` — slug → integer-PK

Each `ConfigurationHandler::export()` receives this `$mappings` array and
replaces integer-PK references with slug values before the export document is
serialised. The translated fields are:

| Entity | Field translated | Mapping key used |
|--------|-----------------|-----------------|
| `Endpoint` | `targetId` (type `api`/`database`) | `source.idToSlug` |
| `Endpoint` | `targetId` (type `register/schema`) | `register.idToSlug` + `schema.idToSlug` |
| `Endpoint` | `inputMapping`, `outputMapping` | `mapping.idToSlug` |
| `Endpoint` | `rules[]` | `rule.idToSlug` |
| `Synchronization` | `sourceId` (type `api`/`database`) | `source.idToSlug` |
| `Synchronization` | `sourceId` (type `register/schema`) | `register.idToSlug` + `schema.idToSlug` |
| `Synchronization` | `targetId` (type `api`/`database`) | `source.idToSlug` |
| `Synchronization` | `targetId` (type `register/schema`) | `register.idToSlug` + `schema.idToSlug` |

For `register/schema`-typed IDs, the value in the database is
`"<registerId>/<schemaId>"` (two integers joined by `/`). The export splits on
`/`, translates each half independently via its respective slug map, and
reassembles as `"<registerSlug>/<schemaSlug>"`. This is documented in
`EndpointHandler.php:66-76` and `SynchronizationHandler.php:72-83`.

**Translation at import time (slug → ID)**

`ConfigurationService::importConfiguration()` (`lib/Service/ConfigurationService.php:731`)
calls `resetMappings()` to populate the `slugToId` direction, then delegates to
each handler's `import()` method. Import handlers use
`$mappings['<type>']['slugToId'][$slug]` to resolve the local integer PK
for each slug reference. If a slug is not found in the target environment (e.g.
a referenced Source does not exist), the slug value is left as-is and a
database constraint violation or null FK will surface the missing dependency.

**Import ordering enforces dependency resolution**

`importConfiguration()` processes entity types in dependency order
(lines 753–799): sources first (no dependencies), then mappings, then rules,
then endpoints (depend on sources and mappings), then synchronizations (depend
on sources, mappings, and endpoints), then jobs (depend on synchronizations,
endpoints, and sources). This ordering ensures that by the time a handler
resolves a slug reference, the referenced entity's `slugToId` mapping has
already been populated.

**Post-chain-B uuid interaction**

After chain B's storage migration runs, all integriq entities are stored
as OR `ObjectEntity` rows identified by uuid. The uuid is the in-environment PK;
the slug remains the cross-environment portable reference. Chain B's migrator
copies `uuid` from the legacy table verbatim (`openspec/changes/openconnector-register-storage/proposal.md:73`),
preserving existing uuid stability. The `ConfigurationService` translation layer
continues to use slug-based maps post-chain-B; the `getIdToSlugMap()` /
`getSlugToIdMap()` mapper methods will be rewritten in chain C to query OR
`ObjectEntity` rows by schema, but the two-way slug translation contract is
unchanged.

## Consequences

- Configurations are portable across environments as long as the human-readable
  slugs match. Slug uniqueness within a resource type is the administrator's
  responsibility.
- A missing slug in the target environment causes a silent null or a database
  error, not a human-readable validation message. A future improvement should
  add a pre-import validation pass that reports missing slug dependencies.
- Register and schema slugs belong to OpenRegister's namespace, not
  Integriq's. Cross-system slug mismatches (e.g. the register exists but
  under a different slug) are invisible to `importConfiguration()`.
- Chain B's uuid migration MUST NOT change entity slugs; the migration
  preserves existing slugs unchanged to maintain portability continuity.
- After chain C, `getIdToSlugMap()` and `getSlugToIdMap()` on each mapper will
  query OR `ObjectEntity` rows. The `ConfigurationService` class is unaffected;
  only the mapper implementations change.

## Evidence

- `lib/Service/ConfigurationService.php:96-131` — `$mappings` property
  docblock: describes the bidirectional `idToSlug` / `slugToId` structure and
  its purpose ("During export: Used to replace entity IDs with their
  corresponding slugs / During import: Used to replace entity slugs with their
  corresponding IDs").
- `lib/Service/ConfigurationService.php:188-219` — `resetMappings()`: populates
  eight entity types' bidirectional maps from mapper `getIdToSlugMap()` /
  `getSlugToIdMap()` calls.
- `lib/Service/ConfigurationService.php:270-298` — register and schema ID
  collection loop for `register/schema`-typed `targetId` / `sourceId` values
  before export.
- `lib/Service/ConfigurationHandlers/EndpointHandler.php:53-97` — export path:
  `targetId` translation by `targetType`, `inputMapping`/`outputMapping`
  translation, `rules[]` translation.
- `lib/Service/ConfigurationHandlers/EndpointHandler.php:115-166` — import path:
  reverse slug→ID translation for the same fields.
- `lib/Service/ConfigurationHandlers/SynchronizationHandler.php:59-86` — export
  path: `sourceId` translation for `api`/`database` and `register/schema`
  `sourceType` values.
- `lib/Service/ConfigurationService.php:731-802` — `importConfiguration()`:
  dependency-ordered import (sources → mappings → rules → endpoints →
  synchronizations → jobs).
- `openspec/changes/openconnector-register-storage/proposal.md:73` — chain B
  migrator preserves `uuid` verbatim from legacy tables.
