## 4. Proof

- [ ] 4.1 On a live instance, push a verzoek with three bijlagen to the STAM endpoint (pre-production HMAC mode, a local file server as DSO-LV), run cron, and verify the three files are on the request object in Files and nothing appeared under `/DSO-verzoeken`
  - NOT PASSED (live run 2026-10-04, throwaway Nextcloud 35 + postgres, OpenRegister development 98a3469, https file server with a local CA). Two identity gaps block it:
    1. The STAM endpoint is anonymous. A correctly signed push answers 202 but saves nothing: OpenRegister refuses `create` on `dso_verzoek` for user Anonymous. The verzoek is lost while DSO-LV is told it was received.
    2. `FetchDsoAttachmentsJob` runs in cron with no user. The raw re-read of the admin-only source is refused, so the token is missing, and the save of the outcome is refused (`update` for Anonymous). Entries stay `pending`.
    OpenRegister's `runAsSystem()` docblock rules out elevation for inbound requests, so the intake needs a named identity to act as. That is a decision, not a fix in this change.
  - What did pass, with an admin session on the push and the admin user active around the real `FetchDsoAttachmentsJob::run()`: three bijlagen downloaded with the Bearer token, `stored` with file ids, tagged `dso-bijlage` in the object folder, byte-identical (sha256); a 404 bijlage ended `failed` after 3 attempts with `attachmentMissing: true`; nothing under `DSO-verzoeken`.
